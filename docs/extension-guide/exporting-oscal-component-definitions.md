# Exporting OSCAL Component Definitions (v4.0 / 8B)

OSCAL [Component Definition](https://pages.nist.gov/OSCAL-Reference/models/v1.1.2/component-definition/json-outline/) documents are how a product describes — in NIST's machine-readable format — which security controls it implements. EmbedIQ emits one per generation when the operator opts into the `oscal-component` output target, so compliance platforms (Drata, Vanta, OSCAL-aware FedRAMP audit pipelines) can ingest the harness as evidence directly.

8A handled the input side: importing NIST catalogs and FedRAMP-style profiles into the domain-pack pipeline. 8B is the output direction.

## Opting in

`oscal-component` is **not** in `DEFAULT_TARGETS` — adding it would change every existing generation's output. Opt in explicitly:

```bash
# CLI flag
npm start -- --targets claude,oscal-component

# Environment variable
EMBEDIQ_OUTPUT_TARGETS=claude,oscal-component npm start

# Or programmatically
orchestrator.generate({
  profile,
  targetDir,
  targets: [TargetFormat.CLAUDE, TargetFormat.OSCAL_COMPONENT],
  domainPack,
})
```

When selected, a post-pass step in the synthesizer emits one file:

```
.embediq/oscal/component-definition.json
```

The post-pass runs after every other generator finishes, so the document's artifact manifest names every file emitted in the same run. Adding `oscal-component` to your target set never alters any other generator's output — existing goldens regenerate byte-identically.

## What the document contains

A valid OSCAL 1.1.2 Component Definition with:

- **Metadata** — title (industry/role), version (EmbedIQ producer version), oscal-version (`1.1.2`), last-modified timestamp, remarks describing the document's purpose.
- **One component** with `type: software`, titled by the profile's industry + role, with:
  - **Component-level props** — producer (`EmbedIQ`), producer-version, profile-industry, profile-role, artifact-count, and one `generated-artifact` prop per file in the run (the full manifest, with `class: embediq.relativePath`).
  - **One `control-implementations[]` entry per compliance framework on the resolved domain pack.** Each entry's `source` is the framework's `key` (e.g. `hipaa`, `nist-800-53-rev5`); description and props carry framework identity.

## Feeding into compliance platforms

The document conforms to the OSCAL Component Definition v1.1.2 JSON schema, so any OSCAL-aware platform can import it directly. Sample workflows:

- **Drata / Vanta** — both platforms accept OSCAL component definitions as evidence of control-implementation claims; ingest via their evidence-upload APIs and the framework's `source` value (e.g. `hipaa`) maps onto the control libraries they maintain.
- **FedRAMP 20x pipelines** — when paired with an OSCAL profile import on the input side (see [`writing-oscal-imports.md`](writing-oscal-imports.md)), the round-trip produces a complete artifact set: profile → tailored framework → generated harness → component-definition citing the same framework. Feed both into the FedRAMP package and the audit trail is OSCAL-native end-to-end.
- **OSCAL-aware oscal-cli / Compliance Trestle** — both tools can validate the JSON against the published schema.

## What's NOT in 8B

For the 8B first cut, `implemented-requirements[]` is left as an empty array on each control-implementation entry. The document surfaces *which frameworks* the harness intends to address, not *which specific control IDs* are implemented by which generated artifacts. That per-control mapping requires either:

- A static control-to-artifact mapping table EmbedIQ maintains per framework, or
- Per-artifact OSCAL annotations that generators emit alongside their content.

Either path is non-trivial and reserved for a follow-up iteration. Until then, downstream platforms can use the framework-level claim plus the artifact manifest to do their own coverage analysis.
