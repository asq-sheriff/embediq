How agent isolation & sandboxing actually works

It's a handoff: EmbedIQ generates the enforcement config; your deployment environment and MDM enforce it. EmbedIQ is not itself a sandbox.

  1. You choose the deployment environment + posture admin, once
    Where the agent runs — a managed laptop, a dev container, a virtual desktop (Azure Virtual Desktop / Windows 365), or an ephemeral cloud dev box. That choice is the isolation boundary.
  2. EmbedIQ generates the config EmbedIQ
    deploy/claude-code/managed-settings.json with "sandbox": { "enabled": true } and a non-wideable deny list (no PHI/PII path reads, no raw egress), plus a .devcontainer for the container posture.
  3. Microsoft Intune (or Jamf) delivers & locks it your MDM
    Intune pushes the file to an OS path the developer can't edit, so the sandbox is required, not optional, and can't be switched off locally. This is the step that turns a config file into enforcement.
  4. The OS sandbox confines the agent at runtime the OS + Claude Code
    Claude Code's native sandbox — Seatbelt (macOS) or bubblewrap (Linux & WSL2, including inside AVD) — restricts the filesystem and network at the kernel level.

What it does

  • Requires & locks the native OS sandbox fleet-wide, beyond a developer's reach
  • Pins a deny floor (PHI/PII paths, egress) the developer can't widen
  • Scaffolds dev-container / VDI isolation for stricter postures

What it doesn't — honestly

  • EmbedIQ produces the config; it is not the sandbox or the MDM — enforcement depends on Intune delivering it and the OS sandbox running
  • Nothing is locked until Intune actually pushes it; without an MDM it's a recommended local setting, not a lock
  • It's Claude Code-specific — other agents have no native sandbox, so isolate those via the dev-container / VDI environment instead
  • Opt-in: set no posture and no sandbox config is emitted. EmbedIQ doesn't provision Intune, the VDI, or the cloud — it ships the config + runbook; you operate the environment
